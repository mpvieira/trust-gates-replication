# Study Protocol: Trust Gates on Agent-Authored Pull Requests



**Purpose.** Provide the evidence the editor and Reviewer 1 asked for: that trust gates surface confirmed defects in industry-tool-generated code that passed conventional CI and human review, measured on real pull requests at a scale well beyond the classroom pilot. A single retrospective study; the built-in baseline is that every PR studied was already merged as green and reviewed.

**Design principle.** Every claim in the revised paper maps to a measured quantity here. Where no comparison exists, the protocol does not license an effectiveness claim.

## 2. Data source

AIDev dataset (Li et al., MSR 2026; arXiv 2602.09185; Hugging Face `hao-li/AIDev`): 932,791 agent-authored PRs across 116,211 repositories from OpenAI Codex, Devin, GitHub Copilot, Cursor, and Claude Code. Use the **curated subset** (33,596 PRs from 2,807 repositories with >100 stars), which includes review comments, commits, and linked issues; these are required to establish that a defect escaped human review.

Framing for the paper: production open-source code generated by the same commercial agents industry uses, merged by maintainers under real CI. Industry code generation without a corporate partner.

## 3. Inclusion criteria

A PR qualifies if all hold:
1. Merged; CI reported success on the merge commit (from timeline events). Repositories without CI excluded.
2. Modifies executable source, not only docs, config, manifests, or generated files.
3. Adds or modifies at least one test, or changes code covered by existing tests.
4. Net change 20–800 lines.
5. Primary language Python, TypeScript/JavaScript, or Java (mutation tooling: mutmut or cosmic-ray, Stryker, PIT).
6. PR description or linked issue states intended behavior well enough to yield at least one requirement. PRs where a human rewrote the principal change before merge excluded.
7. Builds and passes its own tests at the merge commit in a clean container.

Record every exclusion with reason; report the funnel in the replication package.

## 4. Sampling

Stratify by agent (five strata). Targets:
- **100 PRs** for the automated battery (G1, G2, G5).
- **40 PRs**, a stratified random subsample of the 100, for manual analysis (requirement elicitation, classification, G4, triage by two raters).

Apply criteria 1–6 before drawing; apply criterion 7 during reconstruction and replace failures from the same stratum. Pre-register frame and quotas on OSF before drawing.

## 5. Procedure per PR

**Step 1. Reconstruct.** Check out merge commit in a pinned container; run build and tests; record CI jobs that ran, test count, and line coverage of changed lines. This is the baseline evidence record.

**Step 2. Elicit and classify (manual subset).** Two raters, from title, description, and linked issue only, blind to the diff: extract atomic requirements; classify each with the procedure in Appendix A; resolve disagreements by discussion. Report Cohen's κ before resolution. One rater is external to the author team.

**Step 3. Run gates.** Each emits an evidence record (Appendix B).

| Gate | Failure mode | Mechanism | Runs on |
|---|---|---|---|
| **G1 Interface reality** | Hallucinated interfaces | Resolve every import, external call, and referenced package in the diff against the manifest, installed environment, and public registry. Flag unresolvable or version-incompatible references. | 100 |
| **G2 Test independence** | Coupled implementation and tests | Mutation testing scoped to changed lines: mutation score and surviving mutants. Flag mirror assertions (expectations that are literal copies of implementation constants). | 100 |
| **G5 Gate sensitivity** | Weak evidence base | Inject 10 faults into changed code (Appendix C operators); run only the PR's own tests; record detection rate. | 100 |
| **G4 Claim–implementation correspondence** | Assumption injection; silent non-execution | Extract each behavioral claim in the PR description; write one targeted check that fails if the claimed behavior is absent; run it. Status per claim: supported / unsupported / not checkable. | 40 |

(G3 boundary probing from the earlier draft is dropped for cost; note in future work.)

**Step 4. Triage (manual subset; automated findings on the other 60 triaged by one rater with a 20% double-coded check).** Each finding is one of: **confirmed defect** (contradicts stated requirement or unambiguous project convention; reproducible), **undocumented limitation** (defensible behavior but PR claims more than it delivers, or an ambiguity resolved silently), **false positive** (equivalent mutant, tool artifact, misread requirement).

For confirmed defects record failure mode (Appendix C), hypothesis category of the violated requirement, severity (Appendix C rubric), and **downstream confirmation**: search later commits, issues, and PRs in the repository for a fix or report of the same defect. Report downstream-confirmed defects as a separate row; they are the strongest evidence in the study.

**Step 5. Escape criterion.** A confirmed defect "escaped conventional practice" if CI passed on the merge commit, no review comment references the defective behavior, and the defect is present in merged code.

**Step 6. CEL statements (manual subset).** One claim–evidence–limitation record per PR from Steps 2–5. Count claims supported vs. recorded as limitations. Select two for the paper as real replacements for the illustrative Figure 2.

**Step 7. Effort.** Machine time per gate; analyst minutes for Steps 2, 4, 6.

## 6. Metrics

- Escaped-defect rate: PRs with ≥1 escaped confirmed defect / PRs analyzed, with 95% Wilson interval, overall and by agent.
- Downstream-confirmed defect count and rate.
- Confirmed defects by failure mode × hypothesis category.
- G2 mutation score distribution and G5 own-suite detection rate distribution.
- Claim support ratio.
- Inter-rater κ for classification and triage.
- Effort per PR, per gate, per confirmed defect.

## 7. Analysis

Descriptive with intervals. No cross-agent significance testing; agent comparison is not the paper's claim. For RQ3, tabulate defects against hypothesis category and report whether cannot-guarantee requirements carry a disproportionate share relative to their frequency (χ² if expected counts permit; otherwise report proportions only).

## 8. Threats and mitigations

| Threat | Mitigation |
|---|---|
| Gates target the failure modes the paper names; finding them is circular | Open "other" code in triage; report modes the taxonomy did not anticipate |
| Requirement elicitation from PR text is subjective | Two raters blind to diff; κ reported; PRs with no agreed requirement excluded |
| Equivalent mutants inflate G2 | Manual equivalence check on surviving mutants in the manual subset; rate reported |
| Open source ≠ enterprise code | Acknowledge; the relevant property is that artifacts come from the same industry agents under real CI and review |
| Language scope | Stated as scope; distribution reported |
| Author investment | OSF pre-registration of protocol, quotas, gate definitions, codebook; external rater on manual subset |
| Downstream confirmation biased toward noticed defects | Reported as a lower bound |
| No controlled fault population | Stated limitation; detection rates against known faults left to future work |

## 9. What the results support

**Supportable:** trust gates surface confirmed defects in industry-agent-generated code that passed CI and review, at a measured rate and cost; a subset were later confirmed by the projects; defects concentrate in predictable hypothesis categories; agent-generated test suites have measured (in)dependence from the code they test.

**Not supportable, state as limitations:** production incident effects; longitudinal evidence accumulation (downgrade the Trust Gates sentence Reviewer 3 flagged to a hypothesis); detection rate against a known fault population; team adoption dynamics beyond the pilot.

## 10. What goes in the paper vs. the replication package

**Paper (≈1 page):** one table (defects by failure mode and hypothesis category, with escaped and downstream-confirmed counts), one chart, two real CEL statements, one sentence each on mutation scores, κ, and effort. Classroom study demoted to a short teachability paragraph.

**Replication package (cited):** this protocol, codebook, gate implementation, container images, sample list with exclusion funnel, all evidence records, triage sheets, effort logs.

## Appendix A. Trust-hypothesis classification procedure

Apply in order; stop at first match.

1. **Would violation be a security, safety, data-integrity, or compliance failure, or make the system unfit for its primary purpose?** → **Must-hold.** The team must be able to produce strong evidence; if it cannot, the requirement or architecture must change.
2. **Does correct behavior depend on resolving a specification ambiguity, on external state the artifact cannot observe, on completeness over an open-ended input space, or on behavior with no reference implementation?** → **Cannot-guarantee.** State the limitation; add containment or review.
3. **Is occasional deviation tolerable if detected and handled operationally?** → **May-fail.** Monitor; define incident handling.
4. None → not a trust hypothesis (likely a design preference). Record and skip.

Record answers to 1 and 2 even when 1 matches: a top-priority requirement that is also ambiguity-dependent is exactly the case where priority-based classification fails and this procedure does work.

## Appendix B. Evidence record (required fields)

```
gate_id, gate_type, linked_hypothesis_ids[]
artifact_ref (repo, commit, files)
exercised        # inputs/paths/mutants actually checked
assumptions      # preconditions the gate relied on
result           # pass | findings[]
not_evaluated    # what the gate could not or did not check
tool_versions, timestamp, machine_time_s, analyst_time_min
```

A record without `not_evaluated` is invalid. This field is the operational difference between a trust gate and a quality gate.

## Appendix C. Failure-mode codebook, fault operators, severity

| Mode | Definition | G5 operators |
|---|---|---|
| Hallucinated interface | Reference to nonexistent or wrong-signature function, endpoint, package, or option | Rename imported symbol; call plausible nonexistent method |
| Edge-case failure | Correct on typical input, wrong at a boundary | Off-by-one on a limit; drop empty-input handling; remove encoding/overflow handling |
| Assumption injection | Ambiguity resolved silently in one direction | Flip strict/permissive default; swap inclusive/exclusive bound; change timezone or encoding assumption |
| Claim–implementation divergence | Comments, docs, metadata, or PR text claim behavior the code does not perform | Leave a documented flag unread; return success without performing the action; log "validated" without validating |
| Other | Anything not above | — |

Severity: **blocking** — violates a must-hold requirement or causes data loss or security exposure; **major** — violates a may-fail or cannot-guarantee requirement with user-visible consequence; **minor** — deviation with no functional consequence.
